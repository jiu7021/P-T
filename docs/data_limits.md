# 데이터의 한계

이 문서는 "무엇을 할 수 없는가"를 먼저 못 박기 위한 것이다.
아래 한계는 설계 단계에서 이미 반영되어 있으며, 결과 해석 시 반드시 함께 읽어야 한다.

---

## L1. Carinthia-S는 비구조화(unstructured) 층이다

- 데이터셋은 **패턴이 없는 웨이퍼 층 1개**에서 취득된 SEM 이미지다.
- 셀 어레이·라인/스페이스·콘택홀 같은 **주기 구조가 없다.**
- 따라서 반도체 SEM 결함 검출에서 흔히 쓰는 **주기성 기반 이상 탐지
  (die-to-die / cell-to-cell 비교, 푸리에 도메인 주기 제거)를 적용할 수 없다.**
- 대안: 데이터셋이 제공하는 전문가 검증 마스크를 이용한 **지도학습 세그멘테이션**.

### 결과적으로 주장할 수 없는 것
- "패턴 층 결함까지 일반화된다" → 주장 불가. 학습에 쓰인 층이 1종뿐이다.
- 층/공정 조건이 바뀌면 성능이 유지된다는 근거가 이 데이터에는 없다.

## L2. 패턴 층 SEM 공개 데이터가 없다

라인/스페이스, 콘택홀 등 패턴 층 SEM 결함 데이터셋은 imec 계열 등에 존재하나
자유 다운로드 대상이 아니다. 본 프로젝트는 패턴 층을 다루지 않는다.

## L3. 존재하지 않는 라벨 — 만들어내지 않는다

| 없는 것 | 왜 없나 | 이 프로젝트의 대체 방식 |
|---|---|---|
| 셀 단위 Fail address 비트맵 | 공개 데이터 없음 | 규칙 기반 판별기 + 합성 예제. **AI 판정이 아님을 화면에 명시** |
| 결함 이미지에 붙은 "원인 공정" 라벨 | 공개 데이터 없음 | 문헌 기반 룩업 테이블(`config/cause_map.yaml`) + 근거 병기. 확정 판단은 사람 |
| 항목별 테스트 결과와 소요 시간 | 공개 데이터 없음 | 물리 가정 기반 합성. 공간 상관 구조만 WM-811K 실데이터에서 가져옴 |

**이 셋은 어떤 경우에도 모델의 학습 타깃으로 삼지 않는다.**
없는 라벨을 지도학습으로 만들어내면 결과 전체가 무의미해진다.

## L4. WM-811K 자체의 한계

- 라벨은 전문가가 부여했으나 **패턴 라벨의 판정 기준이 공개되어 있지 않다.**
  경계 사례(Loc vs Edge-Loc 등)의 라벨 잡음 가능성을 배제할 수 없다.
- 라벨 보유 웨이퍼는 전체의 약 21%이며, 라벨링 대상 선정이 무작위였다는 근거가 없다.
  → 라벨 보유분만 쓰는 본 프로젝트의 통계는 **전체 라인 분포의 대표성을 주장하지 못한다.**
- 공정 조건, 제품 종류, 테스트 항목 정보가 데이터에 없다.
  → 웨이퍼 맵에서 원인 공정을 직접 역추적하는 것은 불가능하다.

## L5. Carinthia-S에는 웨이퍼·배치 식별자가 없다 → 이미지 단위 분할 (수치 낙관 편향)

**확인 완료 (2026-08-21).** `carinthia-s.csv`의 열은 `image_path`, `mask_path`,
`filename`, `label` 넷뿐이고, `filename`은 32자리 16진 UUID다.
웨이퍼 ID, 로트, 배치, 취득 시각 등 **상위 단위로 묶을 수 있는 정보가 전혀 없다.**

따라서 학습/검증 분할을 이미지 단위로 할 수밖에 없다. 그 결과:

- 같은 웨이퍼의 인접 영역이 학습/검증 양쪽에 들어갈 수 있다.
- **Module B의 성능 수치는 낙관적으로 나온다.** 실제 신규 웨이퍼에 대한 성능이 아니다.
- 이 수치를 "일반화 성능"이라고 부르지 않는다. 보고 시 항상 이 한계를 병기한다.

## L6. 결함 클래스의 이름이 공개되어 있지 않다

Carinthia-S 설명서와 원본 Carinthia 설명서를 모두 확인했으나(2026-08-21),
**여섯 클래스는 `1`~`6` 숫자로만 표기되며 결함 종류 이름이 어디에도 없다.**
(particle, scratch, residue 등 어떤 결함 용어도 두 문서에 등장하지 않는다.)

이는 Module B-3의 원인 공정 룩업 설계에 직접 영향을 준다.

- 숫자 클래스에 임의로 "particle", "scratch" 같은 이름을 붙이는 것은 **금지**한다.
  근거 없는 라벨 생성이며, `cause_map.yaml`의 근거 원칙에 정면으로 위배된다.
- 대안(Module B-3에서 확정): 마스크에서 **관측 가능한 형태 특징**
  (면적, 종횡비, 선형성, 개수, 위치)을 계산해 **형태 유형**을 정의하고,
  형태 유형 ↔ 원인 공정 후보를 문헌 근거와 함께 매핑한다.
  숫자 클래스는 참조로만 병기한다. 형태는 이미지에서 직접 측정되는 사실이다.

## L7. 클래스 6은 "결함 없음"이며, 분포가 극단적으로 치우쳐 있다

데이터셋 설명서 기재 사실:

- **클래스 6(227장)은 결함이 보이지 않는 이미지다.** SEM 장비 정렬 오차로 결함이 아닌
  인접 영역을 촬영한 경우 발생한다. → 결함 클래스가 아니라 **취득 실패 이미지**다.
- 클래스 5는 **전체 4장**뿐이다(설명서에도 "only four images"로 명시).
- 클래스 2는 8장, 클래스 1은 55장.
- 클래스 3이 4,008장(87.3%)으로 지배적이다.

결과적으로:

| 클래스 | 장수 | 학습/평가 가능성 |
|---:|---:|---|
| 3 | 4,008 | 가능 |
| 4 | 289 | 가능 |
| 6 (결함 없음) | 227 | 가능하나 "결함 클래스"로 다루면 안 됨 |
| 1 | 55 | 통계적으로 불안정 |
| 2 | 8 | **분할 시 검증셋에 1~2장. 성능 수치의 신뢰구간이 무의미** |
| 5 | 4 | **분할 자체가 성립하지 않음** |

- 주 지표는 **macro-F1**으로 하되, 클래스 2·5의 F1은 표본 수 때문에 사실상 잡음이다.
  macro-F1 하나만 보고하면 오해를 낳으므로 **클래스별 표본 수를 항상 함께 표기**한다.
- accuracy 단독 사용 금지(클래스 3만 찍어도 87.3%).
- 세그멘테이션 지표(IoU/Dice)는 클래스 무관하게 픽셀 단위로 계산되므로
  분류보다 상대적으로 안정적이다. Module B의 주 성과 지표는 세그멘테이션 쪽에 둔다.

## L8. 그 밖에

- 두 데이터셋은 서로 다른 라인·제품·시점의 것이다. Module A(웨이퍼 맵)와
  Module B(SEM 이미지)를 **같은 웨이퍼의 데이터인 것처럼 연결하지 않는다.**
  대시보드에서 두 모듈을 잇는 것은 "업무 흐름의 재현"이지 "동일 웨이퍼 추적"이 아니다.
  이 문구를 화면에 표기한다.
