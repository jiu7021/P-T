## Module A-2. 공간 특징 추출 — **WM-811K 실데이터**

실행: `.venv/bin/python src/features/spatial.py` (2,128,718행, 약 25초)

### 스캔 순서 정의 (미래 정보 누수 방지의 기준점)

**serpentine(뱀 모양)**: 행 0은 왼→오른쪽, 행 1은 오른→왼쪽, 이하 반복.

- 근거 **(통상범위)**: 프로버는 행 끝에서 시작점으로 되돌아가지 않고 방향을 바꿔
  진행하는 편이 스텝 이동 거리가 짧다.
- 단방향 래스터로 정의하면 모든 행에서 "이미 테스트된 이웃"이 항상 왼쪽에만
  생겨 좌우 비대칭 편향이 특징에 들어간다. serpentine은 행마다 방향이 바뀌어
  이 편향이 상쇄된다.

### 추출한 특징 (다이당 12개)

| 특징 | 정의 | 미래 정보 여부 |
|---|---|---|
| `r_norm` | 유효 다이 무게중심 기준 거리 / 최대 거리 | 기하학적, 무관 |
| `edge_dist`, `edge_dist_norm` | 유효 영역 거리 변환(EDT) 값 | 기하학적, 무관 |
| `nb8_tested_cnt` | 8-이웃 중 **이미 테스트된** 다이 수 | 과거만 |
| `nb8_tested_fail_rate` | 위 이웃들의 불량 비율 | 과거만 |
| `nb_r2_tested_cnt` | 유클리드 반경 2 이내 이웃 중 이미 테스트된 수 | 과거만 |
| `nb_r2_tested_fail_rate` | 위 이웃들의 불량 비율 | 과거만 |
| `prev_wafer_fail` | 같은 로트 직전 웨이퍼 동일 좌표 불량 여부 | 이전 웨이퍼, 무관 |
| `scan_rank`, `scan_progress` | 웨이퍼 내 테스트 순번 / 진행률 | 자기 순번, 무관 |

명세의 "반경 2 이내 이웃 불량 비율"에는 원래 '이미 테스트된' 조건이 붙어 있지
않았으나, **8-이웃과 동일하게 과거 다이만 쓰도록 제한했다.** 반경 2에만 미래
정보를 허용하면 그 경로로 누수가 들어온다.

### 잘 안 되는 부분 — 숨기지 않고 기록한다

1. **Loc의 F1이 0.451로 가장 낮다.** 실제 Loc 40장 중 Edge-Loc으로 10장,
   Center로 7장이 갔다. Loc / Edge-Loc / Center는 "국소 밀집 불량이 어디에
   있는가"만 다른 라벨이라 경계가 연속적이다. WM-811K는 라벨 판정 기준을
   공개하지 않으므로(`data_limits.md` L4) 라벨 자체의 모호성과 모델의 한계를
   이 결과만으로 분리할 수 없다.
2. **Scratch의 recall이 0.564로 낮다.** Edge-Loc 8장, none 6장으로 샜다.
   Scratch는 불량률이 10.89%로 낮아(표 A-1) 선형 구조가 64×64 리샘플링에서
   흐려지는 것이 원인으로 보인다. 확인하지 않은 추정이다.
3. **과적합.** train loss는 0.016까지 떨어졌으나 val macro-F1은 30에폭 부근
   0.82에서 포화했다(60에폭 기준 val 0.811, best 0.823). 데이터 증강이나
   정규화를 더 넣으면 개선 여지가 있으나, 성능이 이 프로젝트의 주장 대상이
   아니므로 추가 튜닝하지 않고 한계로 남긴다.
4. **val 0.823 → test 0.763.** val로 가중치를 고른 만큼 val이 낙관적이다.
   보고 기준은 test다.

### Grad-CAM — 라벨만 내놓지 않는다

마지막 conv 특징맵(64ch, 8×8)에 대한 클래스 점수의 기울기를 채널 중요도로 삼아
가중합하고 64×64로 되돌린다. 훅 대신 `torch.autograd.grad`로 직접 받는다.

## Module E. Fail Address 불량 모드 판별 — **주소 데이터는 전부 합성**

실행: `.venv/bin/python src/sim/fail_address.py`

> 셀 단위 Fail Address 비트맵은 **공개 데이터가 존재하지 않는다**(`data_limits.md` L3).
> WM-811K는 다이 단위 합불만 제공하며 칩 내부 셀 주소는 없다.
> 여기의 주소는 전부 합성이며, **규칙 기반 판별기**로 처리한다. 모델이 아니다.

### 데이터 계층 — 혼동하지 말 것

| 계층 | 단위 | 본 프로젝트의 데이터 |
|---|---|---|
| 웨이퍼 맵 | 다이 1개 = 점 1개 (pass/fail) | WM-811K **실데이터** |
| Fail Address | 다이 **내부** 셀 주소 (X, Y) | **합성** (공개 데이터 없음) |
| SEM 이미지 | 결함 1개의 확대 이미지 | Carinthia-S **실데이터** |

### 주소 표기

**16진수다. 12진수가 아니다**(a~f가 나타난다). 주소 공간은 X 16bit / Y 12bit로
잡았다 — **(가정치)**. SK하이닉스 공개 영상의 Fail Address 화면에서 X가 4자리
16진수(`1a3d`), Y가 1~3자리(`0` ~ `2e1`)로 표기된 것을 근거로 자리수만 맞췄다.
비트 폭의 절대값은 결론에 영향을 주지 않는다. 판별이 주소의 절대값이 아니라
**같은 주소를 공유하는 fail의 개수와 분포**로 이루어지기 때문이다.

영상 화면의 Y 값(`0,1,10,11,20,21,…` / `2a0,2a1,2b0,2b1,…`)을 16진수로 풀면
**16 간격으로 2개씩 묶인 구조**다. 합성기의 `stride=16, pair=2`가 이 형태를 재현한다.
실제 주소 매핑 구조는 공개되어 있지 않다 — **(가정치)**.

### 불량 모드 5종

| 모드 | 형태 | 물리적 해석 |
|---|---|---|
| `single_bit` 싱글비트 | 고립된 단일 셀 | 셀 개별 결함, 랜덤 파티클 |
| `row_fail` 로우성 | 같은 X 다수 | 워드라인 단선/단락, 로우 디코더 이상 |
| `column_fail` 칼럼성 | 같은 Y 다수 | 비트라인 단선/단락, 센스앰프 이상 |
| `block_fail` 블락성 | 좁은 X·Y 구간에 밀집 | 매트 단위 전원/기준전압 이상, 국소 공정 결함 |
| `cross_fail` 크로스 | 로우 + 칼럼 동시 | 교차점 회로/상위 제어 이상. 리페어 자원 소모 최대 |

### 판별 규칙 — 점수는 '설명 비율'이지 확률이 아니다

각 구조가 설명하는 fail 집합의 크기 비율을 점수로 쓴다. `single_bit` 점수는
**어느 구조로도 설명되지 않은 fail의 비율**이며, 합집합으로 계산한다.

> 초기 구현에서 `single_bit`를 "최대 구조 하나가 설명하지 못한 비율"로 계산해
> row 50% + column 50%인 크로스가 싱글비트와 동점이 되었다. 이때 크로스 판별
> 정확도가 200회 중 27회(13.5%)였다. 합집합 기준으로 고쳐 200/200이 되었다.

상위 두 후보의 점수 차가 `ambiguous_margin`(0.20) 미만이면 **경계 사례로 표시하고
단정하지 않는다.**

### 판별 결과 예시 (합성 row_fail, fail 22건)

```
     X | Y             판별: 로우성 (row_fail)  점수 0.909
  -----+-----          근거
  4aa8 | c8c             최다 X = 0x6323 : 20건 (90.9%)
  6323 | 1b8             최다 Y = 0xc8c  : 1건  (4.5%)
  6323 | 1b9             최밀 블록 0x6323~0x6332 / 0x1b8~0x1c7 : 2건 (9.1%)
  6323 | 1c8
  6323 | 1c9           ← X가 고정된 채 Y만 16 간격 쌍으로 늘어선다
  6323 | 1d8
   …
```

### 자기검증 — 합성한 모드를 판별기가 되찾는가

각 모드 200회, 산발 잡음 0~3건 포함:

| 합성＼판별 | single_bit | row_fail | column_fail | block_fail | cross_fail |
|---|---:|---:|---:|---:|---:|
| single_bit | **200** | 0 | 0 | 0 | 0 |
| row_fail | 0 | **200** | 0 | 0 | 0 |
| column_fail | 0 | 0 | **200** | 0 | 0 |
| block_fail | 7 | 0 | 0 | **193** | 0 |
| cross_fail | 0 | 0 | 0 | 0 | **200** |

**일치 993/1000 (99.3%)**

block_fail 오판 11/400건의 원인을 확인했다: fail 총수가 적을 때(중앙값 10건)
블록 창 안의 fail이 5건에 그쳐 `block_min_count=6` 임계를 넘지 못한다
(count 미달 7건, ratio 미달 1건). **임계값의 한계이지 판별 논리의 오류가 아니다.**

> 이 수치는 '판별기가 의도한 형태를 구분한다'는 최소 확인일 뿐이다.
> 합성과 판별이 같은 가정 위에 서 있으므로 실제 라인 데이터에 대한 성능이 아니다.

### 임계값 민감도 — 전부 가정치이므로 반드시 본다

자기검증 일치율(각 모드 120회):

| 임계값 | 변화에 따른 일치율 |
|---|---|
| `line_min_count` | 2: 99.3% / 3: 99.3% / **4: 99.3%** / 6: 96.2% / 8: 93.7% |
| `line_min_ratio` | 0.15: 99.3% / 0.2: 99.3% / **0.3: 99.3%** / 0.4: 97.5% / **0.5: 82.7%** |
| `block_min_count` | 3: 99.7% / 4: 99.7% / **6: 99.3%** / 8: 98.8% / 10: 96.2% |
| `block_min_ratio` | 0.2: 99.3% / 0.3: 99.3% / **0.4: 99.3%** / 0.5: 99.3% / 0.6: 98.2% |

(굵은 값이 채택한 기준값)

- **`line_min_ratio`가 가장 민감하다.** 0.5로 올리면 82.7%까지 떨어진다.
  라인성 fail에 산발 잡음이 섞이면 비율이 희석되기 때문이다.
- `block_min_count`를 3~4로 낮추면 99.7%로 오르지만, 합성 데이터에서만 확인된
  값이다. 실제 산발 불량을 블록으로 오인할 여지를 남기지 않기 위해 6을 유지한다.
  **유리한 쪽 수치를 택하지 않았다.**

### 흐름

```
SEM 이미지 → 마스크에서 형태 측정 → cause_map.yaml 룩업
   → 후보 + 근거 + 출처 제시           (AI가 하는 일은 여기까지)
      → 엔지니어가 판정                (사람이 결정)
         → verdicts.jsonl 에 누적
            → 준비도 판단 → 충분하면 학습 데이터로 내보내기
```

### 설계 원칙 4가지

1. **AI는 후보와 근거만 제시하고 원인 공정을 판정하지 않는다.**
   `show` 명령은 후보·근거·출처·주의사항을 나열할 뿐 선택하지 않는다.
2. **append-only.** 기존 기록을 수정하지 않는다. 판단이 바뀐 이력도 데이터다.
3. **표본이 부족하면 학습을 거부한다.** 적은 표본으로 그럴듯한 모델을 만드는 것이
   이 프로젝트에서 가장 위험한 실패다. `export`가 종료코드 1로 거부한다.
4. 데모용 가짜 판정은 `source="demo"`로 표시하고 학습 대상에서 제외한다.

### 학습 준비 기준 — **(가정치)**

| 조건 | 값 |
|---|---:|
| 엔지니어 판정 총 건수 | ≥ 100 |
| 30건 이상 모인 공정 종류 | ≥ 2 |
| 공정당 최소 건수 | ≥ 30 |

근거: 공개된 기준이 없다. 클래스당 수십 건 미만이면 검증셋 분리조차 성립하지
않는다(Module B의 class 5가 4장이라 F1이 무의미했던 것과 같은 문제).
**이 값을 넘겨도 성능이 보장되지는 않는다.** 하한일 뿐이다.

### 기록 스키마

| 필드 | 내용 |
|---|---|
| `ts` | 판정 시각 |
| `image_id`, `label`, `morphology` | 대상과 측정된 형태 |
| `candidates_shown` | 판정 시점에 제시된 후보 목록 (표가 개정돼도 당시 맥락이 남는다) |
| `verdict_process` | 엔지니어가 선택한 공정 |
| `off_list` | 후보 목록 밖 판정 여부 |
| `confidence` | high / medium / low |
| `rationale` | 판정 근거 자유 입력 |
| `engineer`, `source` | 판정자, engineer/demo 구분 |
| `model_suggestion` | 현재 `null`. 학습 모델이 생기면 그때 기록한다 |

**후보 밖 판정을 막지 않는다.** 룩업 표가 불완전할 수 있고, 후보 밖 판정이
쌓이는 것 자체가 `cause_map.yaml`을 개정할 근거가 된다. `stats`가 그 건수를
따로 보고한다.

### 현재 상태

판정 0건. `export`는 거부된다(종료코드 1). 정상 동작이다.
